# eli-solid: one method for every visual, each app's own look
**Date**: 2026-10-30
**Status**: Approved
**Touches**: `docs/how-it-works/craft-skills.md`, `docs/how-it-works/agents.md`, `setup/templates/AGENTS.md` (visuals block, routing line 8), every skill's `## Visuals`, `README.md` (What's inside)

## TL;DR
- New craft skill `skills/eli-solid/` in the free plugin, adapted from the owner's work explainer skill; routed like the other craft skills.
- Content and structure fixed: picture first, real names in mono with a plain caption, set section order.
- Two section orders: Explain (how a thing works) and Decide (the ask and the recommendation up top).
- Look order: a `## Look` section in the project's `AGENTS.md` or `CLAUDE.md`, or the user's words → `system.md` → `direction.md` → theme tokens → default.
- Default look: the Solid Vibes look, "Notebook in fern green". Its colours, Newsreader + Instrument Sans, radii 8/14/20.
- Roles fern lacks are derived and marked: a warm ochre `--hot`, tints, cell, band, a 3:1 `--line-strong`.
- Role split: `--link` (chrome) and `--ok` (done) are fern green; `--hot` (not done, critical path) is warm ochre.
- `templates/style.html` keeps the source classes and markers on role tokens; `references/look.md` has the mapping and contrast pairs.
- The generated `## Visuals` block becomes a pointer: when and where to show; `eli-solid` holds the method.
- Each skill's `## Visuals` line names `eli-solid`; one-line edits in 12 files.
- Docs: README (eighteen skills), CHANGELOG, `craft-skills.md`, `agents.md`, a decision note.
- After merge, outside `go`, owner-confirmed: close sv-pro PR #10, remove its worktree and branch.

## Context
The owner's work explainer skill is kept privately, outside every repo. It makes pages that read well:
- big pictures and few words;
- real names;
- one idea per section;
- rejected options greyed;
- gaps flagged.

Solid Vibes visuals today follow only the short page rule in the generated `## Visuals` block of a project's `AGENTS.md`, and they vary. The owner wants every Solid Vibes visual to share one method and structure, while each app keeps its own look. That covers explainers, decision pages, plan pages, mockups and tables. It goes in the free plugin so more people get it.

A first attempt was sv-pro PR #10, which added `ui:visuals-in-app-look` to the `ui` pack. Review rejected it:
- it imposed a house style (mono on every label);
- its starter CSS made every app's pages identical;
- it fixed section skeletons and table columns;
- it broke its own one-accent rule.

A plan for an sv-pro skill (sv-pro `plans/2026-10-30-eli-solid.md`) is superseded by this one.

Good pages already exist and show what to aim for:
- a one-line `/* Layout: … */` comment;
- the app's real tokens, light and dark, and its real fonts;
- the product's own components drawn with real data;
- the picture first;
- the ask and the recommendation easy to find;
- anything not yet built drawn dashed.

## Constraints

  - **Behavior here, data in the project.** The default look is behavior; a project's look stays in the project.
  - **Generated vs seeded.** The `AGENTS.md` blocks between `solidvibes:begin/end` markers are generated and overwritten by `init`. They are never a per-project source. `tests/init_blank.sh` asserts the line "Show visuals for decisions, flows and screens." stays in the visuals block.
  - **Audience.** Anyone; plain words; every term explained.
  - **Skill descriptions** are trigger conditions in the user's phrases.
  - **No `~/.claude` or `/Users/` paths** in skills.
- **The local strip denylist** matches the source's product name as a case-insensitive substring. That name is also a common English word, so avoid it everywhere, prose included. Run `scripts/strip-check.sh` locally; CI has no denylist.
- **Skill naming:**
  - `docs/decisions/2026-10-24-skill-names-are-public-api.md`: a new skill is cheap.
  - `docs/decisions/2026-10-30-craft-skills.md`: craft skills are routed, never called by name.
- **Craft skill shape:**
  - `skills/writing/SKILL.md` and `skills/accessibility/SKILL.md`: "How you talk to the user", the contract read, the basics, a "With Pro" line, `## Visuals`.
- **Risk areas touched:**
  - Step 8 deletes a worktree and a branch in sv-pro ("anything that deletes"). It runs outside `go`, after merge, on the owner's yes.
  - No other risk area changes.

## Approach
A craft skill, the sixth. Craft skills say how to do one thing well and load inside other steps. Visuals happen exactly that way: `brainstorm`, `plan`, `design` and the rest "show a visual". Each skill's `## Visuals` line names `eli-solid`. The generated `## Visuals` block in projects becomes a pointer: when to show a visual, where it goes (`.solidvibes/agents.md`), and that `eli-solid` makes it. That leaves one method list, in the skill. The description catches direct page requests only. A plain "how does X work?" still gets a plain answer.

The method is fixed and the look comes from the project. The skill keeps the work skill's seven page rules, its classes and its update procedure, and drops everything tied to one company. `templates/style.html` keeps the source's class names, layout and markers, on a full set of role tokens. Its defaults are the Solid Vibes look plus a few derived tokens the method needs. For a project with a look, the agent sets the role tokens from it, and copies the app's own token names only when it draws mockups of the app's components.

Where the agent shows no HTML, the method still applies; the template does not. The generic profile shows Mermaid or a table.

Ruled out:
- **An sv-pro skill.** The owner wants it in the free plugin.
- **The sv-pro `ui` pack (PR #10).** The review rejected it.
- **The generated `## Visuals` block as the per-project look source.** `init` overwrites it.
- **Keeping the Visuals block's bullet rules beside the skill.** Two method lists drift; the block points instead.
- **`--hot` as error red.** It reads as an error, and the fern system keeps red for real errors.
- **`--hot` as fern green.** It would clash with success, which shares the primary green.
